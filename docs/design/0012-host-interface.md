The current design of this area, and nothing else. Edit it in place when the design changes; git holds the history. It describes the design only, never the work still to do.

## 1. Purpose and scope

This area decides every way a host, a worker or the owner reaches Baley, and how Baley reaches back:

- the per-session server: its stdio connection, protocol revisions, the project it serves and the bounded queue its calls share;
- the host adapter: how Baley knows which host is connected and what that host can do;
- the wire: the tools, the operation contract, refusals, bounded reads by identity, long work;
- how Baley's questions reach the owner and how the owner's answers are recorded;
- served instructions and the stubs a host loads: skills and per-rung agent definitions, written at install;
- the command line;
- install, updates and doctor: delivery, registration, hook, sandbox and stubs, on Claude Code.

It does not decide the content of any instruction (each area owns its own), the settings ([0003](0003-configuration-and-routing.md)), the guard's decisions ([0010](0010-guard.md)), or how Baley's release artifacts are built and published ([#14](https://github.com/jcrenshaw-dev/baley/issues/14)).

Hand-offs: every area's operations are served here; the work order composer ([0002](0002-system-design.md) section 8) hands this area the work orders to deliver; [0003](0003-configuration-and-routing.md) gives the route and the host alias tables; [0010](0010-guard.md) gives the hook's decisions; the ledger records every call's refusal or receipt.

In the component view of [0002](0002-system-design.md) (Figure 4) this area is the host interface component and the host adapter among the ports.

## 2. Terms

| Term | Meaning |
|---|---|
| Host | Claude Code, the program the owner works in, whose session starts workers as subagents and connects to Baley over MCP. |
| Session | One host conversation, with its own Baley server over stdio. |
| Worker | A subagent the host session starts for one work order. It shares its session's connection. |
| Server | The Baley process a session starts: one per session, over stdio, serving the session and its subagents. |
| Adapter | The per-host code that knows what a host can do and translates: how a work order is launched, how effort is passed (the rung's own level, run at the model's highest supported level at or below it, HST-R12), how a question reaches the owner, how a long call behaves, how an answer is shaped. |
| Client info | What a host sends when it connects: its name and version. |
| Operation | One typed request under the `query` or `apply` tool, named by a string that is only ever added, never renamed or removed. |
| Refusal | A typed answer that a request was not done, with a code and a place. |
| Identity | The name by which a record or an instruction is read. A record is read by a kind plus keys, and an instruction by its short name, such as `bal-help`. Neither is ever a path. |
| Part | One bounded piece of a served record or instruction, at most 24,576 bytes, with the identity of the next part. |
| Work order | The complete dispatch for one worker ([0002](0002-system-design.md) section 8): its role, subject, attempt, route, agent stub, the instructions it lists by identity, version and hash, and its inputs. It is recorded as one `work_order.issued` and read by its worker through `document` by its id. |
| Delivery | How a work order reaches its worker. The operation that issues the order answers the session with the order's id, the agent stub to launch, a one-line prompt naming the id and a launch sentence. The session starts that stub with the Agent tool and the prompt, passing the route's model as the Agent tool's `model` parameter when the route has one. The worker reads its order by the id in its prompt. The session changes nothing in it. |
| Stub | A file a host needs on disk to list or launch something, rendered by Baley at install from its tables: frontmatter and one line pointing at Baley. |
| Skill stub | A stub for one front door, which a session invokes by name: `<Claude folder>/skills/<identity>/SKILL.md`. |
| Agent stub | A stub Claude Code runs a work order's worker as, one per role and rung, named `bal-<role>-<rung>`, thirty in all: `<Claude folder>/agents/<name>.md`. Its frontmatter fixes the rung's effort, inherits the model and names the session's `baley` server, and its one body line sends the worker to its order. |
| Relay | The host session putting Baley's question to the owner and returning the answer. |
| Elicitation | The MCP request by which a server asks the host to show the person a form. |

## 5. Commands and operations

### baley_version (tool)

- **Inputs:** none.
- **Outputs:** `version`, `os` and `arch` of the running binary.
- **Refusals:** `unknown-host`, a `failed` answer for a client that is missing or unsupported (HST-R4), and `invalid-arguments` for any argument.

### baley_query (tool)

- **Inputs:** `operation` and its typed arguments; an optional `part`.
- **Outputs:** the operation's typed result, or one part with the next part's identity.
- **Refusals:** `unknown-operation`, `operation-unavailable` (a spelling an earlier server served, naming the build that replaces it), `invalid-arguments` (the reason names the field), plus the operation's own codes. A project that cannot be prepared is not a refusal: the call is answered `failed`, from the table under `baley_apply`.

Query operations are the reads of every area: `help`, `schema`, `document` (a record by identity: capture, draft, roadmap, story, work order, plan, phase, run, review, verification), `document-search`, `instruction` (an instruction by identity), `progress`, `next` ([0013](0013-next-action-and-progress.md)), `why`, `recall`, `search` ([0014](0014-support-families.md)), `route`, `status` operations per area.

`help` takes an optional command `name`, `schema` takes `tool` and `for`, `instruction` takes `identity`, and `document` takes `identity` as an object tagged by `kind`: `{"kind": "capture", "id": "<capture id>"}`, `{"kind": "draft", "digest": "<digest>"}`, `{"kind": "roadmap"}`, `{"kind": "story", "id": <story id>}`, where a story id is an integer, or `{"kind": "work_order", "id": "<order id>"}`. Each of these four operations takes an optional one-based `part`. Each served operation schema is self-contained, with nested shapes inlined. The input schemas of `baley_query` and `baley_apply` carry the same shapes as properties beside `operation`, so a host is given `identity` as an object and `part` as an integer rather than free text. An argument two operations type differently, such as `identity`, is an `anyOf` of their shapes, and each shape ends by naming the operations that take it and whether each requires it. Other properties stay allowed, so a retired spelling still reaches the server and is answered `operation-unavailable`. The built `document` schema accepts those five identity kinds, each refusing fields its kind does not take, and any other kind is `invalid-arguments`. An answer that fits in 24,576 bytes comes whole. A larger one comes in parts, each carrying `bound`, `part`, `body` and `next`, where `next` is the next part's number, or null on the last part, and joining the bodies in order gives the answer's bytes. The bound counts body bytes, not the encoded result, and the tool result carries each answer both as text and as structured content. `instruction` answers with the text and its identity, version and hash. `document` answers a capture's text, whole or in parts, and the whole answer and every part carry the identity with the capture's kind, phase, byte count and recording time. When the project released the capture's body, it answers a tombstone with that project's purge reason from its view instead, even while another project still holds the bytes. If only another project purged the body, this project still reads its text. A global body lookup that reports a purge after the view was read triggers a fresh read of this project's view: only its own tombstone supplies the reason. If the view does not confirm that purge, the read answers `failed` `ledger-unavailable` instead of borrowing a global reason. A draft answers with its `kind`, `digest`, the `recorded_at` of its latest submission and the `submission` as recorded. When this project purged the draft's body, it answers the same fields with a `tombstone` holding `state` `purged` and this project's reason from the `draft` view in place of the submission, and the body is not opened; a body lookup that finds the body gone after the view read answers `failed` `ledger-unavailable`, with no second view read. A digest not written as 64 lowercase hexadecimal characters names no draft and is answered `unknown-draft` without a read. The roadmap answers the accepted `description`, the `phases` in roadmap order with their numbers, names, goals, status, dependencies and story ids, and the `stories` in priority order with their ids, wording, status, phase and truth count; a project with no approved scope answers no description and empty lists. A story answers that story nested under `story`, so its own status never stands in for the answer's. A work order answers `order`, its document as the `work_order` view holds it: `id`, `request` (the id of its chain's first order), `parent` (the failed order it retries, or null), `role`, `subject` (`start` for the start planner's order), `attempt`, `route` (the route record, [0003](0003-configuration-and-routing.md) section 6), `agent`, `instructions` (each `{identity, version, hash}`), `inputs` (each `{name, body}`), `state` (`pending`, `failed` or `answered`), `seq`, `recorded_at`, `failure` (`{reason, seq, recorded_at}` or null), `drafts` (the digests of the drafts submitted under it, first seen first) and `child` (the retry issued from it, or null). Beside it the answer carries `accepted`, the digest of this project's start approval when that digest is among the order's drafts and otherwise null, read from the project's events since an approval names only a digest; `follow`, one fixed sentence telling the worker to read each instruction the order lists, in order, with `baley_query` `instruction` by its identity, and to follow them; and `inputs`, each with its `name`, `hash` and `bytes` and its `text`. An input this project purged answers a `tombstone` `{"state": "purged", "reason": ...}` with this project's own reason, read from its `retention` stream, in place of the text. A body the store no longer holds whole for any other reason answers `unavailable` with its state, `reduced`, or `purged` with no reason when only another project's purge released the bytes, so another project's reason is never shown. Nothing is rebuilt from current input. A body found purged after the first read of the releases makes the read look at this project's releases again. A draft, the roadmap, a story and a work order are cut into parts of their answer's JSON text when it is larger than one part, as `help` is. The same reads serve `baley scope preview`, `baley scope show` and `baley story show` on the command line. The refusals are `instruction-unavailable`, which names the build that owns an identity not yet served, `unknown-instruction` for any other identity, `no-such-capture` for a capture id the project does not hold, `unknown-draft` for a digest no submission in the project has, `no-such-story` for a story id the accepted roadmap does not hold, `no-such-work-order` for an order id this project's `work_order` view does not hold, `help-part-not-found`, `schema-part-not-found`, `instruction-part-not-found` and `document-part-not-found` for a part that does not exist, and `invalid-arguments` for a field the shape lacks, so an `instruction` field, the identity a session sends on `baley_apply`, is refused on any read, `document` included. `help`, `schema` and `instruction` need no project, `document` and `route` need one, and no read records anything.

`route` takes exactly one of `role` and `work_order` and answers the route record, the agent stub and the policy version it was explained at, or null with a note. It reads and judges the settings as a write does, then stops: it admits no checkout, runs no policy step and creates or advances no attempt. [0003](0003-configuration-and-routing.md) section 5 gives its inputs, outputs and refusals.

### baley_apply (tool)

- **Inputs:** `operation`, a request id, which is a UUID in lowercase hyphenated form, and its typed arguments. `capture`, `project-start`, `work-order-fail` and `work-order-retry` also take `instruction`, the identity of the instruction the session follows. `scope-submit` takes no `instruction`: it names the work order it answers, and its caller carries that order's instruction evidence. The ten change operations take none either, since their shapes have no place for it, and their front doors' texts tell the session to send none.
- **Outputs:** the operation's typed receipt; a replay of the same request id returns the same receipt.
- **Refusals:** as `baley_query`, plus `request-id-reuse` (same id, different payload), which records nothing, and the operation's own codes. A request id in any other form is refused `invalid-arguments` naming `request_id`. The registry judges `instruction`, and an unknown identity or one not served is refused `unknown-instruction` or `instruction-unavailable` naming `instruction`, with nothing recorded.

For `capture`, `project-start`, `work-order-fail` and `work-order-retry`, the registry's instruction evidence is attached to the caller before preparation begins. The same caller reaches checkout admission, the policy step and the operation's command, so their `checkout.seen`, `policy.effective`, `capture.recorded`, `work_order.issued` or `work_order.failed` and completion events carry it. A call that names no instruction adds no evidence.

`scope-submit` takes a request id, `work_order`, the id of the start planner's work order the submission answers, as that order's receipt gave it, and `submission`, the whole start submission: `description` with `what`, `core_value` and `constraints`; `stories`, each with a local `label`, a `sentence` and a `status` of `active`, `deferred` or `excluded`; and `roadmap`, the phases in order, each with a `name`, a `goal`, a `detail`, `depends_on` as positions in `roadmap` counted from 1, and the `stories` it delivers by label. The input schema declares the submission an object, so a host sends it as one; the request shape still takes it untyped, and the arguments are judged before anything is prepared, in this order: the shape, the request id, the order's id, which must be a UUID in lowercase hyphenated form or is refused `invalid-arguments` naming `work_order`, then the submission whole. A field that is missing, blank, of the wrong type, unknown or out of range is refused `malformed-submission` with its `section` and `field` in the details, never `invalid-arguments`; a story listed by two phases is refused `story-double-assigned`; and phases that depend on each other in a cycle are refused `dependency-cycle`. None of these records anything. The write is prepared under the session's caller carrying the order's id. The write's own check then reads the order from the project's `work_order` view: an id the view does not hold is refused `no-such-work-order`, and an order that is not the start planner's, role `planner` and subject `start`, is refused `wrong-work-order`, both naming `work_order`. It then reads the project's events, and a project whose start is already approved is refused `project-already-started`. Each of these records nothing. An order passes in any state, so a later submission naming an order an earlier one already answered is recorded as the newest draft. Once the check passes, the command's caller also takes the order's instruction evidence, so every event of the submission's transaction carries the order and the instructions it listed. The order rides on the caller and never in the submission, so the draft's digest is the content's alone, while the request digest covers the order too, so one request id cannot answer two orders. An accepted submission is recorded as a draft: one `scope.submitted` on the `project` stream naming its digest, with the submission's canonical JSON stored as a `record` payload. The digest is the SHA-256 of that JSON, so the same content has the same digest from any session. The `work_order` view adds the digest to the order's `drafts`, and a pending order becomes `answered`. The receipt carries `digest`, `kind` (`start`), the `stories` and `phases` counts and `recorded_at`, never the content. Every submission records, so resubmitting a digest makes it the newest draft again. A retry with the same request id and content replays its receipt, and the same id with other content is refused `request-id-reuse`. A submission whose exact bytes were purged from the ledger is answered `failed` `text-purged` ([0004](0004-starting-a-project-and-changing-scope.md) section 5).

Each change to accepted scope is its own operation, listed after `scope-submit`: `project-describe`, `phase-declare`, `phase-edit`, `phase-reorder`, `phase-withdraw`, `story-declare`, `story-edit`, `story-reassign`, `story-drop` and `backlog-reorder`. Each takes a request id and `submission`, the change's members, which name phases by number and stories by id ([0004](0004-starting-a-project-and-changing-scope.md) section 5 lists them per change). As for `scope-submit`, the input schema declares the submission an object and the request shape takes it untyped; it is judged whole under the kind the spelling names before anything is prepared, and a fault in it, a `kind` the caller sent included, is `malformed-submission` naming its `section` and `field`, never `invalid-arguments`, with nothing recorded. The write's own check then judges the change against accepted scope as the ledger holds it, after the replay lookup and before the settings read, checkout admission and the policy step: a change before the start is approved is refused `project-not-started`, and each kind's scope rules give their own codes, such as `no-such-phase`, `order-incomplete`, `dependency-order`, `story-undecided` or `phase-has-dependents`, all with nothing recorded. An accepted change is recorded as a draft as a start is, one `scope.submitted` naming its digest, kind and target, with its body, the members with the kind added, stored as a `record` payload; its transaction confirms the scope the check read has not moved and otherwise answers `failed` `ledger-busy`. The receipt carries `digest`, `kind` and `recorded_at`. Replays, `request-id-reuse` and `text-purged` are as for `scope-submit`, and a retry of a completed change replays its receipt whatever the check would say now. The owner's `baley phase reorder`, `baley phase withdraw`, `baley story reassign`, `baley story drop` and `baley backlog reorder` submit the same change through the same functions on the command line (see [Approvals on the command line](#approvals-on-the-command-line)).

Three work-order operations are listed last: `project-start`, `work-order-fail` and `work-order-retry`. Each is served only by the session server, since an operation that only issues or settles a work order has no command-line form. Each judges its own arguments first, the shape, the request id and then its own fields, each a `refused` answer with nothing recorded. An `instruction` it names is judged by the registry as for `capture`. Then each prepares a write with its own check, after the replay lookup and before the settings, as `scope-submit` does. Each answers a replay from its record, `request-id-reuse` for a request id reused with other arguments, and `failed` `ledger-busy` with nothing recorded when the work orders, the start or the stored inputs its check read moved before its transaction ran. Its receipt is recorded with its command, so a retry under the same request id gets the same receipt and issues nothing new.

- **`project-start`** issues the start planner's work order. It takes a request id, `brief`, the brief's whole text, which the session reads in its own sandbox and sends, and an optional `instruction`. The server reads no file for the brief. A brief that is empty or only whitespace is refused `brief-blank`, and one over 65,536 bytes of UTF-8 `brief-too-large`, both naming `brief`. The check refuses `project-already-started` once the project's start is approved, and `start-order-pending` while a start planner order is pending, naming that order in `details.work_order`. The order is recorded as one `work_order.issued` on the project's `roadmap` stream under command kind `project.start`, with the brief stored as a `record` payload and named as the order's one input, `brief`. Its id is a fresh lowercase UUID and also its `request`, its route is the planner's at attempt 1 under the policy the write's policy step recorded, and it lists the instruction `bal-start-planner`, then `bal-start-survey` when the checkout holds existing code ([0004](0004-starting-a-project-and-changing-scope.md), PRJ-R1). The receipt carries `work_order`, `request`, `attempt`, `agent`, `model` (the route's model, or null), `prompt`, `launch`, `recorded_at`, `existing_code`, and `settings` when the settings are missing, as [0004](0004-starting-a-project-and-changing-scope.md) section 5 gives them with every refusal in the order it is judged.
- **`work-order-fail`** records that an order's worker could not launch or returned without a valid result. A session reports a failure: nothing infers one from silence. It takes a request id, `work_order`, the order's id as its receipt gave it, a lowercase UUID, `reason`, plain words that are not blank and hold at most 4,096 bytes of UTF-8, and an optional `instruction`. A malformed id or reason is `invalid-arguments` naming the field. The check refuses `no-such-work-order` for an id this project's `work_order` view does not hold, and `work-order-not-pending` for an order that has already failed or been answered, giving its `state` in `details`. A pending order gets one `work_order.failed`, `{id, reason}`, on the stream it was issued on, under command kind `work_order.fail`, and the view marks it `failed` with that failure. The receipt carries `work_order`, `state` `failed`, `next`, a sentence naming `work-order-retry`, and `recorded_at`.
- **`work-order-retry`** issues the next attempt of a failed order. It takes a request id, `work_order`, the failed order's id, which must be the newest attempt of its chain, and an optional `instruction`. The request digest covers the order alone, so the same retry sent again under its request id replays the same new order and counts one attempt. The check reads the order and each earlier attempt back to its chain's first order, and this project's purge releases, and refuses: `no-such-work-order` for an id the view does not hold; `work-order-not-failed` for an order that is pending or answered, or whose chain an earlier attempt's answer ended, giving the `state` and, for an earlier answer, that attempt's id; `work-order-retried` for an order already retried, naming the retry; and `material-unavailable` for an order one of whose inputs this project purged, naming the input. A retry of the start planner's order is then refused `project-already-started` once the start is approved and `start-order-pending` while another start order is pending, so a project keeps one live start order. The new order is one `work_order.issued` on the parent's stream under command kind `work_order.retry`, with a fresh lowercase UUID, the chain's `request`, the failed order as `parent`, the parent's role, subject and inputs unchanged, the instructions the parent listed at the registry's current version and hash, and the route resolved again under the current policy and catalog at the parent's attempt plus one, one rung up when `escalate_on_failure` is on ([0003](0003-configuration-and-routing.md), CFG-R16). The view sets the parent's `child` to the new order. The receipt carries what `project-start`'s does, with `parent` in place of `settings` and `existing_code`.

No approval operation is served. The owner approves a draft by its digest with `baley scope approve <digest>` on the command line, because over MCP the call comes from the model and nothing proves a person answered, while the sandbox keeps agents from running the command line against Baley's home, where the ledger lives ([ADR 0044](../adr/0044-owner-acts-on-the-command-line.md)). A `baley_apply` call spelled `scope-approve` is not one of its operations and is refused `unknown-operation`.

Apply operations are the writes of every area, each named in its document: scope, story, phase and plan operations (0004, 0005); execution operations (0006); verification operations (0007); review operations (0008); risk operations (0009); landing, milestone, release, undo, pause (0011); capture, task, debug, spike (0014); `answer` (the owner's answer to a relayed question); `worker-exit`; `round-record`; Build 4's `models-return` for a provider list bound to a fetch work order ([0003](0003-configuration-and-routing.md#5-commands-and-operations)).

### Approvals on the command line

Every owner approval is given at the terminal, never through a session (HST-R10, [ADR 0044](../adr/0044-owner-acts-on-the-command-line.md)). For scope it is `baley scope approve <digest>`, which approves any draft a submission's receipt named: a start's from `scope-submit`, or a change's from one of the ten change operations or from the owner's change commands below ([0004](0004-starting-a-project-and-changing-scope.md) section 5). The digest must be written as the receipt writes it, 64 lowercase hexadecimal characters, and anything else is refused before the ledger is read. The command finds its project from its working directory and then runs the approval's first step, which reads the draft and judges it against the ledger outside any transaction. A digest no submission has is refused `unknown-draft`; a draft older than the newest draft of the same change, the same kind and target, `stale-draft` naming the first part that differs; a second start `project-already-started`; and a change draft already approved after its latest submission `draft-approved` naming that approval. A change draft is then judged again against accepted scope as it stands, with the refusals its submission would get now. A draft whose body this project purged is answered `ledger-unavailable`. None of them records anything. The command then reads and validates the settings, admits the checkout and runs the policy step, as the command line's other writes do, and reads the owner: the global `owner.name`, or git's `user.name` read in the command's working directory when it is unset, so a repository's own `user.name` applies there. With neither it refuses `owner-identity-missing`, saying what git did and how to fix it: set `owner.name` with `baley config set --global owner.name="Your Name"`, or git's name with `git config --global user.name "Your Name"`. That refusal comes after checkout admission and the policy step, which stay recorded. The approval is recorded with actor `owner`, the owner's name and Baley's clock when the approval arrives, and its transaction confirms that nothing the first step judged has moved, answering `ledger-busy` with nothing recorded when something has. A receipt prints the kind, digest, owner and time and the phase numbers and story ids the approval recorded and exits 0; a refusal prints `<code>: <reason>`, followed by a stale draft's path or a malformed submission's section and field, and exits 2; a failure exits 1 (`crates/baley/src/scope/command.rs:302-328, 482-531`, `crates/baley/src/scope/approve.rs:96-558`, `crates/baley/src/providers/identity.rs:24-39`).

The owner also submits the five changes that carry only numbers and ids: `baley phase reorder <NUMBER>...`, `baley phase withdraw <NUMBER> [<STORY>=<PHASE>|<STORY>=drop]...`, `baley story reassign <ID> <PHASE>|backlog`, `baley story drop <ID>` and `baley backlog reorder <ID>...`. Each turns its words into the members a session sends for the same change and goes through the same functions as the session's operation: the same judgement of the shape, the same check against accepted scope before checkout admission and the policy step, so a refused change records nothing, and the same recording, so the same content gets the same draft digest from either surface. The draft is recorded as the owner with no caller, under the policy version the step returned, and the command prints the draft's kind, digest and time and the `baley scope approve` command that approves it (`crates/baley/src/scope/command.rs:330-396, 533-551, 592-673`). Declarations, edits and `project describe` have no command, since an agent drafts their text.

### Long-call handle

- **Inputs:** an apply operation that starts long work; later, the same operation with the handle.
- **Outputs:** `completed` with the receipt, or `running` with the handle and how long the call waited.
- **Refusals:** `unknown-handle`, `handle-expired` (HST-R8).

The session's decision worker is separate from long work. It runs accepted decisions to completion even when a caller stops waiting. It frees a completed decision's queue slot before sending its answer, but keeps the drain pending until that send finishes. An empty queue is drained only when no answer is in flight, including after admission closes or waiting decisions are abandoned. A dropped receiver discards its answer and still permits the drain. This ordering covers delivery to the call's receiver, not flushing the transport. At shutdown the server waits up to ten seconds for that drain. At the bound it first abandons waiting decisions. Either way it then makes its one exit checkpoint attempt.

### Installer and baley install

The development installer is `sh install.sh https://<source>`. It takes exactly one argument, a source beginning with `https://`, and removes trailing slashes. It supports Linux and macOS on `x86_64` and `aarch64`, mapping Darwin to `macos` and `arm64` to `aarch64`. It fetches `<source>/<os>-<arch>/manifest` and `<source>/<os>-<arch>/baley`, a plain executable, with `curl -q --proto '=https' --tlsv1.2 -fsSL`. The `-q` prevents curl configuration from changing the requests. There is no archive or published release (`install.sh:92-129, 142-145`).

Both delivery paths read exactly two UTF-8 lines, each ending with a newline, with no extra content:

```text
version 0.2.0
sha256 <64 lowercase hex digits>
```

The placeholder on the second line stands for the executable's SHA-256. A version has exactly three decimal parts, `major.minor.patch`, each fitting `u64`, with no sign or leading zero except a lone `0`. The installer's `verify_download` compares the downloaded executable's SHA-256 with the manifest, using `sha256sum` or `shasum -a 256`. It has no verification bypass. This checks unsigned development bytes only. #14 owns signature verification in both delivery paths at `verify_download`, the trust root, release format and publication (`install.sh:37-71, 147-171`, `crates/baley/src/update/manifest.rs:101-133, 178-201`).

The stable path is `$HOME/.local/bin/baley`, a symbolic link to `$HOME/.local/lib/crenshawdev/baley/versions/<version>/baley`. These paths are the same on Linux and macOS. `BALEY_HOME` and `XDG_*` move neither. `HOME` must be absolute, nonempty UTF-8 without a `..` component. Repeated slashes and `.` components are removed without following folder links. The installation's identity is the resulting stable path text, never its target (`crates/baley/src/update/installation.rs:75-134`).

The script allows an absent stable path or a link whose stored target is exactly the absolute `<versions>/<version>/baley`, with the version spelled by the same rule as the updater. It refuses other occupants and links to folders, and rechecks before activation. A reused staged file must be regular, not a link, have the manifest's digest and be executable. For a new staged file, the script sets mode `755` on the downloaded file before moving it into the versions folder, then moves it to its final name. It creates a temporary link in `~/.local/bin` and moves that link onto the stable path. It removes no version. Its receipt prints `baley: placed version <version> at <stable path>`, then `baley: versions present in <versions folder>:` and the version folders holding regular binaries. A failure of the script's own steps, before its last one, exits 1. The last step runs `"$stable" install`, after the receipt, and the installer ends with that command's exit status (0, 1, 2 or 3, as the receipt section below lists), so a refused or partial install fails the installer. The script itself writes no host wiring, records no install event and seeds no catalog: `baley install` does that (`install.sh:73-90, 173-212`).

`baley install` writes Claude Code's wiring at the stable path and takes setup defaults. Provider choice and acknowledgement belong to `baley config interview` (section 5), and `baley doctor` checks the installed result (below). The script and install ran live with unsigned development artifacts into a disposable `HOME` and an isolated Claude folder (sheet `spikes/host-matrix/install-live-2026-10-11-run1.md`). A new Claude Code session listed the server with its three tools on the `/mcp` screen, answered `baley_version` with 0.0.2 and ran the installed hook (`#inst.after.mcp`, `#inst.after.version`, `#inst.after.hook`). It also answered that it listed both stubs that build placed, `bal-capture` and `bal-help` (`#inst.after.stubs`). A session started before the install answered that it listed no Baley server or tool after it (`#inst.old-session.server`), and reported listing the new stubs at its next turn (`#inst.old-session.stub`, observed with a finding). These three outcomes rest on the session's own answer: the host's line showed only a count of skills, and no file, ledger row or receipt shows the list. Whether a running session finds a newly written stub, and whether it lacks the server and tools, are therefore unverified. Each checkout still needs the owner's `baley init`. The command is `baley install [--host <name>]` (`crates/baley/src/install/command.rs:28-54`, `crates/baley/src/main.rs:43-44, 129`).

- **Inputs:** the host, default `claude-code`, and `HOME`, `CLAUDE_CONFIG_DIR` and the resolved Baley folders. Any other host is refused `unknown-host` before anything else runs, naming the supported hosts from `Host::ALL`. Every executable reference install writes is the absolute stable path, `~/.local/bin/baley`, from the installation layout and never from the running binary's own path (`crates/baley/src/install/command.rs:123-132`, `crates/baley/src/host_artifacts/installed.rs:55-114`).
- **Outputs:** the artifacts in the table below, then the catalog seed and `install.recorded`. Existing owner settings and separately owned registrations are preserved. Replacement needs evidence of Baley's ownership, never a matching name alone (UPK-R2 in [0015](0015-repository-upkeep-and-build-gate.md)).
- **Receipt:** see below. A partial install is never reported complete.
- **Refusals:** see below. Signature or checksum failure activates nothing, in the installer before install runs.

**Where each artifact goes.** The Claude folder is `CLAUDE_CONFIG_DIR` when it is set, else `~/.claude`. A set value must be non-empty, absolute and UTF-8, and its trailing slashes are dropped. `HOME` must be usable even then, because it places the stable path. Nothing else moves these paths: `BALEY_HOME` and `XDG_*` move only Baley's own folders.

| Artifact | Place | Written by |
|---|---|---|
| Guard hook, `permissions.deny` rules and `sandbox` block | `<Claude folder>/settings.json`, one document | Install, through `replace::replace` (a temporary file in the same folder, renamed only if the file's digest is still the one read, never through a link) |
| Skill stubs | `<Claude folder>/skills/<identity>/SKILL.md`, one folder per served front door | Install, through the same replacement |
| Agent stubs | `<Claude folder>/agents/<name>.md`, one file per role and rung, thirty in all, beside any agent file of the owner's | Install, through the same replacement |
| MCP registration `mcpServers.baley` | `$CLAUDE_CONFIG_DIR/.claude.json` when the variable is set, else `~/.claude.json` | Claude Code, by `claude mcp add-json --scope user baley <entry>`. Install never writes this file |

Claude Code rewrites `.claude.json` whole, by rename, again and again while a session runs (`spikes/host-matrix/claude-live-2026-10-08-run1.md:675-679, 759-763`), so a write by Baley could be refused for a changed digest or be written back over by an open session. Baley asks Claude Code to make the change instead. `claude mcp add-json` refuses a name that exists, so replacing Baley's older entry runs `claude mcp remove --scope user baley` first, after the file is read and judged a second time. Each `claude` launch has its own process group, a 30-second timeout, 64 KiB kept per stream, no input and install's own environment. Claude Code relocates its configuration under `CLAUDE_CONFIG_DIR`, and user-scope servers then live in `$CLAUDE_CONFIG_DIR/.claude.json` (read from the installed binary, and a live run stored a user-scope registration in an isolated folder, `spikes/host-matrix/live-claude.md:177`, `spikes/host-matrix/claude-live-2026-10-08-run3.md#ses.b.registered`). Install ran against a live Claude Code 2.1.296: the registration went into the isolated `.claude.json` and the owner's real `~/.claude.json` gained no `baley` entry (`spikes/host-matrix/install-live-2026-10-11-run1.md` `#inst.register.stored`, `#inst.register.real-unchanged`). The entry has `command` the stable path and `args` `["serve"]`, with no `alwaysLoad`, `env` or `type` key. The hook item is the nine-tool matcher with a single command hook that runs the single-quoted stable path and `guard` within 10 seconds (`crates/baley/src/install/registration.rs:19-57`, `crates/baley/src/host_artifacts/registration.rs:20-26`, `crates/baley/src/host_artifacts/hook.rs:13-50`).

**Ownership.** Install proves an artifact is Baley's from the latest `install.recorded` for the host and from this binary's own render. A name or a folder proves nothing.

- A stub is Baley's when its bytes equal this binary's render, or when its SHA-256 is the hash the latest record holds for that identity. A stub that holds other bytes, is a link, or cannot be read refuses the install (`crates/baley/src/install/stubs.rs:26-71`).
- A stub the latest record lists that this binary no longer ships is judged only when the record names it at its own stub path under the current Claude folder, `<Claude folder>/skills/<identity>/SKILL.md` or `<Claude folder>/agents/<identity>.md`, either kind's path counting since the record holds no kind, its identity is one path name spelled exactly (so `bal-capture/` cannot stand for `bal-capture`), and that path is no placed file's path. A record entry naming any other path, such as one under an earlier Claude folder, is never read or touched, so a record cannot point a removal outside a stub's own file, and it stays in the record as it was, so a later install under that folder can still act on it. Install removes the file when it holds bytes whose SHA-256 is the hash the record holds for it and the path is not a link. A file that cannot be read keeps its record entry, since it may still be Baley's. Any other file there is the owner's: it stays, refuses nothing and leaves the record (`crates/baley/src/install/plan.rs:106-207, 368-379`, `crates/baley/src/host_artifacts/installed.rs:106-114`, `crates/baley/src/replace.rs:168-187`).
- A JSON entry is Baley's when it equals this binary's render or what the latest record holds for it. The registration is compared by one rule, shared with composition and the doctor: the same `command` and `args`, `env` absent or empty, and `type` absent or `stdio`. Every other key, `alwaysLoad` included, is ignored. So an `mcpServers.baley` entry that sets any `env` entry is never this binary's, because it can point the server at another ledger, and an `http` or `sse` entry that still holds Baley's command and arguments is not Baley's either, because Claude Code does not launch it through `command` (`crates/baley/src/host_artifacts/compose.rs:177-196`, `crates/baley/src/install/registration.rs:66-115`).
- Older Baley entries leave only on the record's evidence. The `PreToolUse` item the record holds, when it differs from this binary's, and each `permissions.deny`, `sandbox.filesystem.denyRead` and `denyWrite` string the record lists that this binary does not render, are removed by whole-value comparison. With no record, nothing is removed. The owner's own items and rules stay (`crates/baley/src/install/settings.rs:120-170`).
- Running install again on a completed installation changes nothing: composition adds only entries that are absent, a stub whose bytes match is not written, and a registration that is this binary's runs no `claude` command.

**Refusals.** A refusal is judged before any write and places or removes no file under the Claude folder, runs no `claude` command, seeds no catalog and records no `install.recorded`. It prints one line per conflict, names the artifact and its path, and exits 2. Baley's own lock file and ledger store may already exist. Every conflict found is listed, so one run shows all of them (`crates/baley/src/install/plan.rs:229-391`).

| Code | When |
|---|---|
| `unknown-host` | `--host` names anything but `claude-code` |
| `install-ownership-conflict` | A stub holds bytes that match neither this binary's stub nor a hash the record lists for it, or is a link. `mcpServers.baley` in `.claude.json` or in the settings file is not this binary's entry or the record's. A `PreToolUse` item runs another `guard` command and the record does not list it |
| `install-settings-conflict` | The settings file or `.claude.json` is not JSON, is JSON but not an object, is not a regular file, is a dangling link, or cannot be read. A key install adds entries under holds another kind of value. The settings file is a link and a write is needed. A Baley folder is not valid UTF-8, so its deny rules could not be written |
| `install-running` | Another `baley install` holds the install lock |
| `install-lock-unavailable` | The lock file cannot be created, opened or locked, with its path and cause |

Beside these, a `HOME`, `CLAUDE_CONFIG_DIR` or Baley folder value that cannot place the artifacts is refused with its own text, and a store that cannot be opened is reported by the shared renderer with its exit class.

**One install at a time.** Install is exclusive. After it has resolved the folders and the artifact paths, and before it opens the ledger, it takes an exclusive, non-waiting lock on `<Baley home>/install.lock`, a file created with mode `0600` that does not follow a link, and holds it until the record is written. A second install is refused `install-running` before it reads anything, because two runs planning from the same record could leave the record naming hashes the files no longer hold. Closing the file releases the lock, so a crashed install leaves nothing to clear (`crates/baley/src/install/command.rs:56-116, 132`).

**Partial installs.** A partial install writes what it can, names each gap with its fix and exits 1.

- Owner settings that weaken protection are kept and named, never overwritten: `disableAllHooks` or `sandbox.filesystem.disabled` true, any `sandbox.excludedCommands` entry, an absolute `allowRead` or `allowWrite` entry that re-opens a Baley folder, a `~/` or relative entry composition cannot judge, and a path the deny rules cannot render. Each gap says what to remove or change.
- Baley's secure value replaces the owner's `sandbox.enabled` false, `sandbox.failIfUnavailable` false or `sandbox.allowUnsandboxedCommands` true. The replacement is written and the receipt reports the old value, but only when the settings write placed it.
- On Linux without `bwrap` or `socat`, and on a platform without Claude Code's sandbox, the `sandbox` block is held back and the owner's own `sandbox` block is left as it was. The hook, the deny rules, the stubs and the registration are still written. The gap carries the doctor's fix text, which names the package and the commands that install it, and says to run install again.
- While nothing runnable sits at the stable path, the hook and the registration are held back, because they would run a path that does not exist. The stubs, the deny rules and the sandbox block are written. The gap says to run `install.sh`, or to place the binary or a link to it at that path, and run install again.
- A write that fails stops the run. The stubs and the registration after it are reported `not written`, with the cause, and the run still seeds the catalog and records what it did own. A failed `claude` command prints the full `claude mcp add-json` line for the owner to run by hand. Registration and the removal of retired stubs are attempted only when every file write was reached.
- A retired stub that is not removed, because its file cannot be read or its removal failed or was not reached, is reported `not removed` with the cause and keeps its record entry, so the next run can still prove it is Baley's and remove it. A removal whose folder could not be synced did remove the file, but like an unsynced write it is reported and leaves the install partial.

**Write order.** The settings file, then the stubs in manifest order, the skill stubs first and then the agent stubs, then the removal of retired stubs, then the registration through `claude`. The catalog seed follows, in process through `models::seed`, then the record. A refused settings write, such as a file that changed after it was read, is reported in the receipt as `install-settings-conflict`, and an I/O failure as `not-writable` with the path. A removal reads the file's digest again just before it removes the file, never through a link, so a file that changed after it was read is reported `not removed` with `config-conflict`, and an I/O failure as `not-removable` with the path (`crates/baley/src/install/plan.rs:333-353, 427-544`, `crates/baley/src/install/apply.rs:29-137`, `crates/baley/src/install/command.rs:139-221`, `crates/baley/src/replace.rs:168-187`).

**The record.** After the seed, install records `install.recorded` (section 6) with the ownership facts the run left: for each stub the hash of the bytes left at its path, the registration entry and the hook item that are Baley's after the run, and the entries Baley owns in the sandbox and deny lists. A step that did not complete keeps the previous record's entry for that artifact while the file still holds it, so the next run can still recognise Baley's older entry, and a retired stub that was not removed keeps its entry after the stubs this binary ships. A retired stub recorded away from its own stub path keeps its entry as it was. A retired stub that was removed, or whose file is the owner's, leaves the record. The record is written only when it differs from the latest one. A run also names the record it planned from, so a run that planned from an older record cannot overwrite a newer one, which is a second guard beside the lock: it records nothing and the receipt says the record was not written (`crates/baley/src/install/plan.rs:564-681`, `crates/baley/src/install/record.rs:47-118`).

**Receipt.** The lines print in this order (`crates/baley/src/install/receipt.rs:81-256`):

1. `install outcome: complete` or `install outcome: partial`.
2. `baley <version> at <stable path>`.
3. One line per artifact in map order, `<artifact> at <path>: <state>`: the stubs by identity, the registration, the hook and the settings. The states are `written`, `registered`, `replaced`, `unchanged`, `written without the sandbox block` and `not written` with the cause. Then one line in the same form per retired stub install meant to remove, with the state `removed, since this binary no longer ships it` or `not removed` with the cause.
4. The catalog seed line, then any write failure and a `the install record was not written` line.
5. A `replaced <key> ...` line for each owner value Baley's secure value replaced.
6. A `gap: ...` line for each gap, with its fix.
7. When the sandbox block is in the file, two lines saying the sandbox settings apply to the Claude Code sessions that read that file, including projects Baley does not manage, but not to another user's sessions or to sessions that read a different settings file, such as one run with `CLAUDE_CONFIG_DIR` set to another folder, and that managed settings, command-line settings and a project's own `.claude/settings.json` and `.claude/settings.local.json` take precedence over the user settings file for single values such as `sandbox.enabled`.
8. The next steps: start a new Claude Code session, run `baley init` in each checkout, the `updates.auto` switch, `baley update`, `baley config interview` and `baley doctor`.

The outcome is complete only when every artifact is Baley's after the run, there is no gap, the catalog seed is recorded and no write, removal or record failed. The exit status is 0 for complete and 1 for partial, 2 for a refusal, and a store failure uses the shared classes (2 for a refused or blocked store, 3 for a busy, unavailable or read-only one).

**The settings file.** Claude Code reads the user settings file below managed settings, command-line settings, a project's local settings and its shared settings. A project's own settings can therefore override single sandbox values such as `sandbox.enabled`, and a managed policy overrides them all. The sandbox in the user file applies to the Claude Code sessions that read that file, including projects Baley does not manage. Which file a session reads depends on `CLAUDE_CONFIG_DIR`: a session run with the value install saw, with none when none was set then, or with another value that names the same folder, reads the same file and is covered. It does not reach another user's sessions or a session that reads a different settings file, such as one run with `CLAUDE_CONFIG_DIR` set to another folder, and the receipt says so. Baley chose this file because it needs no administrator rights and holds the hook, the deny rules and the sandbox as one document that is composed once. Install writes nothing to `config.toml`: the interview's defaults are the compiled defaults, and a setting the owner changed later is not touched. Provider hosts and `review.reviewers` are written by `baley config interview`, never by install (section 5).

**Limits.** Three cases are not closed. A removal checks a retired stub's digest and then removes the file by name, and Linux has no call that removes a file only while its bytes still match. A process that swaps the file, or a folder above it for a link, between the two can have install remove a file it did not judge. The stub and settings writes have the same window between their last check and the rename (`crates/baley/src/replace.rs:116-187`). Between install's second read of `mcpServers.baley` and the `claude mcp remove` that follows it, another writer can change the entry, so the remove can delete an entry install did not judge ([#251](https://github.com/jcrenshaw-dev/baley/issues/251)). When nothing runnable is at the stable path, install withholds the new hook but still removes an older hook the record lists, so a machine can end with no hook ([#252](https://github.com/jcrenshaw-dev/baley/issues/252)); the gap says so only by naming the empty stable path. The written wiring was observed in live Claude Code sessions on Linux only (`spikes/host-matrix/install-live-2026-10-11-run1.md` `#inst.after.mcp`, `#inst.after.hook`, and the session's own list of stubs, `#inst.after.stubs`, which is unverified); macOS was not run and stays unverified.

Install resolves the folders for its deny paths without pinning folder environment values into the MCP entry or hook. The server, hook and owner commands resolve their own runtime environment and must resolve the same `BALEY_HOME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME` and `HOME` inputs, and the sandbox paths must match the resulting folders. `doctor` reports disagreement instead of certifying a different, unprotected home.

### Sandbox and provider access

The library renders the filesystem and permission proposal below, and `baley install` merges it into the user settings file `<Claude folder>/settings.json`, replacing the example paths with the resolved absolute folders (section 5). The example shows Linux defaults for a home folder of `/home/owner`, with the files a default installation places and, last, the provider hosts the interview adds when both providers are chosen and acknowledged. It lists every skill stub but only the first and last of the thirty agent stubs, `bal-planner-low` and `bal-reviewer-max`: the other twenty-eight follow between them in role order, each role's five rungs from `low` to `max`, each with the same two entries. Each placed agent file is named on its own, and the `agents` folder never is, so the owner's own agent files there stay editable. Install itself writes no `network` block and adds neither API host. It keeps every host the file already holds, as it keeps any unrelated key. The fields follow Claude Code's [sandbox settings](https://code.claude.com/docs/en/sandboxing).

Sandbox filesystem paths use ordinary absolute paths; `Read` and `Edit` rules use `//` for an absolute path. `Edit` covers Write and NotebookEdit. The guard also covers Read, Grep and Glob over the home and config folder, and protects the project file ([0010](0010-guard.md), GRD-R11 and GRD-R13); the placed stubs, the placed settings and registration files and the installed executable are on its list, and the versions folder is its write-only folder. Each write-only file gets a `denyWrite` entry and an `Edit` file rule, with no `Read` rule. In the default layout, the versions folder is `~/.local/lib/crenshawdev/baley/versions`, outside both the PATH folder and Baley's ledger home. Setting `BALEY_HOME` to the versions folder, a folder that contains it, or a version folder inside it is not supported: the home's read denials would cover the staged binaries, so sandboxed commands could not run them. The proposal protects it as a folder: its absolute path in `denyWrite` and `Edit(//<absolute-folder>/**)`, with no `denyRead` entry or `Read` rule, so sandboxed commands can run the binaries inside it. `PlacementMap::write_only_folders` supplies that folder separately from protected files, and the guard's write decision denies writes to the folder and its contents (`crates/baley/src/host_artifacts/placement.rs:290-330`, `crates/baley/src/protected_paths/write.rs:13-31, 75-103`). The live guard derives the same placements from the environment: the stable path and versions folder from `HOME`, and the Claude folder from `CLAUDE_CONFIG_DIR`. It reads no store for them and passes them at `guard_hook::context::judge`, which protects the files once each and the versions folder as a write-only folder. When the placements cannot be derived, because `HOME` or `CLAUDE_CONFIG_DIR` is unusable, the guard cannot clear any path call and fails closed: it denies the six path tools and cannot record, so an ask becomes a deny (`crates/baley/src/guard_hook/context.rs:70-94, 107-178`, `crates/baley/src/host_artifacts/installed.rs:55-114`). The doctor builds its map from the install record (see `baley doctor`). There is no key folder, no provider-tool state exception and no `~/.codex` allowance.

The library renders this shape, without the `network` block, from the resolved folders, the executable, the write-only files and the write-only folders, and reports a supplied path that is not absolute UTF-8, that a rule would read as a pattern, or that ends in a space a deny rule would drop, instead of rendering it (`crates/baley/src/host_artifacts/security.rs:92-110, 144-223`). It composes the shape into an existing settings document, keeping every unrelated key, `sandbox.network` included. Where the shape is composed, Baley's secure values replace a disabled sandbox, `failIfUnavailable` false and `allowUnsandboxedCommands` true, with each replacement reported. Composition reports and retains `sandbox.filesystem.disabled` true, `disableAllHooks` true, and `sandbox.enabled` false, `failIfUnavailable` false or `allowUnsandboxedCommands` true in a document the shape is not composed into, such as one holding only the hook or the registration. It also reports and retains every `sandbox.excludedCommands` entry, whatever it names, since Claude Code runs a listed command outside the sandbox even with `allowUnsandboxedCommands` false; the home or config folder re-opened by an absolute `allowRead` or `allowWrite` entry; a `~/` or relative `allowRead` or `allowWrite` entry, which Claude Code resolves against the owner's home folder or the settings file's place and which composition therefore cannot judge; a differing hook running `guard`; and a `mcpServers.baley` entry with another command or arguments, with `env` entries, or of a transport other than `stdio`. A conflict marks the result incomplete. `baley install` sorts what composition reports into refusals, replacements and gaps (section 5) (`crates/baley/src/host_artifacts/compose.rs:98-175, 206-287`, `crates/baley/src/install/settings.rs:352-489`). The coverage judge reports what the resulting document covers per tool and per read or write (`crates/baley/src/host_artifacts/coverage.rs:281-356`). Any excluded command leaves Bash, Monitor and PowerShell and every write-only file a gap (`crates/baley/src/host_artifacts/coverage.rs:375-398`), and a `~/` or relative allow entry leaves each verdict its list can open a gap, reported as not judged (`crates/baley/src/host_artifacts/coverage.rs:429-442`). Both read only these settings, in the one document they are given: a setting Claude Code also honours, such as `sandbox.enabledPlatforms` leaving out this platform, or one in another settings file, is not seen. The placement projection carries the installed executable path and the separate versions folder (`crates/baley/src/host_artifacts/placement.rs:290-330`). The coverage judge still takes only the home, the config folder and write-only files, so it does not judge the installed versions folder. The doctor's settings check does: it requires the `denyWrite` entry and the `Edit` rule that install renders for that folder, as it requires every other entry install renders (`crates/baley/src/host_doctor/drift.rs:48-99`, `crates/baley/src/install/settings.rs:98-118`). Install applies the composed result to the settings file, and the guard protects the same placements. The `network` block is the interview's, written for the chosen providers through the settings part of the installation writer; neither the library nor install renders a network key.

`baley config interview` takes provider choice and typed acknowledgement after its thirteen settings questions ([0003](0003-configuration-and-routing.md), CFG-R28, section 5). The owner answers `openai`, `deepseek`, both separated by a comma, or `none`, and a blank answer keeps the stored choice (`crates/baley/src/config_command/interview/providers.rs:75-109, 120-187`). For each provider the owner names, the interview shows the warning and takes a typed `yes`. The warning states: Baley never reads your API keys. Keys live in your environment, where every program Claude Code starts can see them, agents and subagents included. Nothing scrubs a key a command prints. Your code goes to the chosen provider under its terms. It then reads the owner, `owner.name`, else git `user.name`, and refuses `owner-identity-missing` before the summary when neither gives a name. The summary before the final `yes` lists every file the writes can change or create (`crates/baley/src/config_command/interview/summary.rs:58-166`). That `yes` records the acknowledgement first, or reuses a current one, adds the chosen providers' API hosts second, writes the global `review.reviewers` list third, and runs the settings `config set` last (`crates/baley/src/config_command/interview.rs:140-185`). The host step is the settings-file part of the installation writer: it reads the user settings file as install reads it, adds each chosen provider's host to `sandbox.network.allowedDomains`, keeps every other key and host, and writes through the digest-checked replacement, so a file changed since it was read is refused as `install-settings-conflict` (`crates/baley/src/install/hosts.rs:91-190`). It takes no install lock, records no `install.recorded`, starts no `claude` command and writes no stub. Hosts are only added, so choosing `none` later leaves them in place. These are separate writes. A failure stops at that step and reports its code and what was written, and running the interview again against the same settings file reads the completed state and applies only the remaining changes. A rerun with neither flag inside a project writes the settings answers to the project file once the global file holds a role value, as [0003](0003-configuration-and-routing.md) section 5 says. The acknowledgement is recorded in the ledger and asked again when the warning changes. A fresh install enables no outside provider, and a reinstall keeps acknowledged choices. Install never acknowledges a warning.

### baley update

Manual `baley update` runs in the foreground whether `updates.auto` is on or off and waits for its receipt. `baley serve` reads the global setting once at startup. When it is true, the server starts the absolute stable path with the hidden subcommand `update detached`, in its own process group, with null input and output, without a parent-death signal or a wait. The detached process has no overall deadline; its individual downloads are bounded. A settings, layout or launch error produces one `baley: update check skipped: ...` line on the server's stderr. The guard never starts or waits for an update (`crates/baley/src/mcp/serve.rs:163-178`, `crates/baley/src/update/detached.rs:9-58`).

The updater reads `updates.source` from global settings. It is an HTTPS address with no default, set with `baley config set --global updates.source=https://<source>`. An absent value refuses `update-source-unset` before opening the store or claiming. The schema requires `https://` followed by at least one character and rejects whitespace, control characters, queries and fragments. The source uses the development layout and two-line manifest above. No host argument or project is required. The CLI resolves the installation from `HOME`, obtains the UTC time and opens the per-user store (`crates/baley/src/update/command.rs:35-70, 108-161`).

The check takes an `update.check` claim before any fetch. Only a new claim permits a download. It judges the stable link as managed only when the stored target is exactly this installation's absolute `<versions>/<version>/baley` and following it finds a regular file. It fetches and parses the manifest, then compares the offered version numerically, major first. An equal or lower version records `current` without fetching the binary. A strictly higher version follows these steps (`crates/baley/src/update/command.rs:241-326`, `crates/baley/src/update/installation.rs:193-225`):

1. Fetch the plain executable through ADR 0028's `reqwest` client, with one client and a separate current-thread Tokio runtime for the check. Requests use HTTPS only, with no proxy, referer, authorization header, project content or provider credential. A manifest has a 20-second request bound and a 64 KiB body bound; the binary has a ten-minute request bound and a 256 MiB body bound. Connection setup is bounded at 20 seconds. Only a complete HTTP 200 response within the body bound is accepted (`crates/baley/src/update/fetch.rs:12-16, 66-83, 94-190`).
2. Pass the bytes through `verify_download`, which checks SHA-256 against the unsigned manifest, with no flag, setting or environment bypass. #14 replaces this verification seam before any release.
3. Stage at `<versions>/<version>/baley`. Reuse only a regular file with the same digest and the owner's execute bit. Otherwise a conflicting entry is refused. A new file is written under a temporary name, set to `755`, synced and renamed to `baley`, then its folder and the versions folder are synced. The claim is confirmed immediately before staging and again before activation (`crates/baley/src/update/deliver.rs:102-157, 197-253`, `crates/baley/src/update/command.rs:351-392`).
4. Recheck the stable link, create a temporary link beside it and activate with one atomic rename exchange of the two links (`renameat2` with `RENAME_EXCHANGE` on Linux, `renamex_np` with `RENAME_SWAP` on macOS). Sync the stable folder and inspect the displaced link. An unexpected occupant is restored by another exchange. An activation error attempts restoration where an exchange occurred; a failed restoration reports the retained temporary entry for inspection. No running executable is overwritten (`crates/baley/src/update/deliver.rs:159-195, 290-408`).
5. Stop lease renewal and complete the claim with its `update.checked` or `update.failed` event in the same transaction. Only after that completion attempt returns does a successfully activated version run its own hidden `baley update seed`, directly from its staged path, to record its compiled catalog without a provider call. The seed has a 60-second deadline and a 4 KiB output bound. A newer view set raised during seeding therefore cannot fence the older updater's completion attempt. The seed still runs if completion failed; the receipt then reports an incomplete record and the new active version (`crates/baley/src/update/command.rs:215-239`, `crates/baley/src/update/record.rs:51-82`, `crates/baley/src/update/seed.rs:34-101`).

Every version is kept. An activation receipt lists the version folders holding regular binaries, including the active version, in numeric order. #14 owns pruning at activation. New sessions start the newly active server, while running servers keep their executable and loaded instructions. Each new hook call follows the stable path. The hook never rebuilds views. The view set is 11: T15's `install` view raised it to 8, the five scope views of Build 4 T3 raised it to 9, Build 4 T4 raised it to 10 with the same views, when it raised the projector versions of the `draft`, `roadmap`, `phase` and `backlog` views for the scope change events, and Build 4 T5 raised it to 11 with the `work_order` view (`crates/baley/src/ledger/open.rs:25-75`). Update events go only into `user`, so the hook adds no new event type to the running session's project. Each rise has a cost. A binary at an older view set is read-only on `user` once a newer binary has written there and brought its views to the newer set, so it cannot write the guard's records, the model catalog or update outcomes that live in `user`. A project is fenced for older binaries only after a binary at the newer view set has used it, and install writes only `user`. The policy step before every project write reads the model catalog's version from `user` and takes 0 when that read is refused for a newer view set, so the session's own project stays writable for an older server (`crates/baley/src/policy_step/mod.rs:48-63`). A binary built before that rule (#258) can write no project once `user` is at a newer view set. Binaries built before T14 cannot write `user` once it holds an update event, binaries built before T15 cannot write it once it holds `install.recorded`, and binaries built before T16 cannot write it once it holds `providers.acknowledged`, because they do not know the event types. In the same way a binary built before Build 4 T3 cannot write a project once it holds a scope event, one built before Build 4 T4 cannot once it holds a scope change event or a `scope.submitted` at version 2, and one built before Build 4 T5 cannot once it holds a `work_order.issued` or `work_order.failed` (`crates/baley-store-sqlite/src/transact.rs:390-406`). No such binary was released, since only development binaries exist. A later binary that raises the ledger epoch can still make an older server read-only under [ADR 0034](../adr/0034-one-server-per-session.md). A running session keeps the server and tools it started with, and a new session loads the installed ones, as its `/mcp` screen and the `baley_version` result show (`spikes/host-matrix/install-live-2026-10-11-run1.md` `#inst.after.mcp`, `#inst.after.version`). That the session started before the install lacked them rests on its own answer (`#inst.old-session.server`). The same session reported listing the new stubs at its next turn, unverified because the host showed only a count of skills (`#inst.old-session.stub`). A manual `baley update` with a session running left that session on its version and gave a new session the new one, and the opt-in check staged a newer version while the session's server had already finished its handshake (`#man.update.receipt`, `#man.s1.keeps`, `#man.s2.new`, `#optin.staged`, `#optin.no-wait`, the last judged under the rule at the run, which the sheet records). The live run put the newer hook beside an older server: the older server kept answering `baley_version`, the newer hook answered through the stable path with its records in `user`, and the older binary's own guard could not record in `user` and turned its ask into a deny (`#old.s3.version`, `#old.s3.hook`, `#old.user-refusal`). The older server's captures in its own project were refused, the defect that the rule above fixes (issue 258, pull request 260) (`#old.s3.capture-1`, `#old.s3.keeps`). The repeat at Build 4 T3's raise of the view set to 9 put a binary at view set 8 that holds the fix beside one at view set 9 (sheet `spikes/host-matrix/older-server-live-2026-10-15.md`). After install brought `user` to view set 9, the older server kept answering and recorded captures in its own project, the newer hook answered through the stable path, and the older binary's own guard could not record in `user` and denied the call. Once the binary at view set 9 had used the project, the older server's next capture was refused `ProjectReadOnly` and nothing was recorded (`older-server-live-2026-10-15.md#old.s3.keeps`, `#old.s3.hook`, `#old.user-refusal`, `#old.s3.fenced`) (`crates/baley/src/ledger/open.rs:25-100`). The raises to 10 and 11 were not repeated in a live session.

The claim protocol in section 6 prevents manual and detached checks from overlapping. Only a detached check refuses a day already claimed, including one claimed manually. Manual checks can retry that day under a fresh request once the installation scope is free.

**Receipt.** The foreground command prints these lines in order (`crates/baley/src/update/receipt.rs:216-336`):

| Result | Lines |
|---|---|
| Current | `update outcome: current`, `active version at <installation>: <version>`, `offered version: <version>`, `nothing staged` |
| Activated | `update outcome: staged`, `staged version: <version>`, `<version> is now the active version at <installation>`, `new Claude Code sessions start <version>; running sessions keep the version they started with`, the catalog seed result, `kept versions: <versions>` |
| Seed result | `the catalog seed of <version> was recorded`, or `the catalog seed of <version> was not recorded: <cause>` |
| Recorded failure | `update failed at <step>: <code>: <cause>`, then the unchanged active version for a download, verification or staging failure, or the freshly observed active version for an activation failure. An unknown managed version is stated as such |
| Completion failed | The activation lines when activation succeeded, otherwise the observed active version, followed by `the record of this check is incomplete: <cause>; the next update check reconciles it` |
| Lease renewal errors | Append `<count> lease renewals failed; first error: <cause>` when any renewal failed |

Current and recorded activation outcomes exit 0, including an activation whose catalog seed failed. A recorded delivery failure or an incomplete record exits 1. Before-claim input refusals and stopped claim gates exit 2, including store errors returned by a claim or its automatic reconciliation. Store-open and user-project setup errors use the shared CLI exit classes: 2 for store refusals or blocked claims, 3 for busy, unavailable, read-only and other store errors. The shared renderer reserves 1 for cleanup failure or an unverified export. Successful receipts go to stdout; refusals and failures go to stderr with `baley: ` on each line (`crates/baley/src/update/receipt.rs:163-196, 216-287`, `crates/baley/src/ledger/display.rs:45-90`).

**Refusals and failure codes.** The bounded delivery codes are also the allowed `update.failed.code` values (`crates/baley/src/update/events.rs:78-126`).

| Code | Meaning |
|---|---|
| `update-source-unset` | Global `updates.source` is absent. The refusal names the command that sets it |
| `update-check-busy` | A claim is active or held for the owner. The receipt names the request and state, and names `baley update resolve` for an owner hold |
| `update-check-not-due` | A detached check found the installation already claimed for that UTC day. A manual check never refuses for this reason |
| `update-not-installed` | The stable path is not a managed installation link |
| `update-network-unavailable` | Client setup, transport, HTTP status or download body bounds prevented a complete download |
| `update-manifest-invalid` | The manifest does not have the exact two-line form, version or digest |
| `update-checksum-mismatch` | The downloaded binary's SHA-256 differs from the manifest |
| `update-staging-conflict` | The staged path already holds something other than the same regular binary with the owner's execute bit |
| `update-activation-conflict` | The stable link changed before activation or the exchange displaced an unexpected occupant |
| `not-writable` | Observing, writing, syncing, renaming or cleaning a delivery path failed. The cause names the path and operation's error |
| `update-interrupted` | The claim was lost or could not be confirmed before staging or activation, or an interrupted check was resolved from local observations |

The claim renderer also has `update-check-needs-reconciliation` for an interrupted gate and `update-check-refused` as a fallback when a refused answer has no code. The command handles an interrupted gate by reconciling and retrying the claim once before rendering it. Invalid `HOME` and folder inputs retain their own diagnostic text. Unreadable or invalid global settings report `config-unavailable` with the path and cause (`crates/baley-core/src/policy/parse.rs:252-256, 273-278`). Store errors use the shared CLI renderer, not the MCP codes `ledger-busy` and `ledger-unavailable`: a busy store says `the ledger is busy; run the command again`, a read-only store names the needed epoch, and other errors retain their store text. There is no `unknown-host` or `update-signature-invalid` path in this command (`crates/baley/src/update/claim.rs:24-33, 218-245`, `crates/baley/src/update/receipt.rs:163-213`, `crates/baley/src/ledger/display.rs:101-146`).

### baley update resolve

`baley update resolve` reads this installation's stable link and version folders and resolves an `update.check` held for the owner. It needs no source setting and makes no network request or activation. It uses `update.reconcile` with owner authority and actor `owner`, records `update.failed` with `update-interrupted` and the observed versions, and releases the installation scope even when the stable path is unmanaged. It does not repair that path; a later check can still refuse `update-not-installed`. Automatic reconciliation is described in section 6 (`crates/baley/src/update/command.rs:72-106`, `crates/baley/src/update/reconcile.rs:200-303`).

With no owner hold it prints `no update check is held for this installation` and exits 0; an interrupted claim not yet held for the owner is left to automatic reconciliation. On resolution it prints `resolved update check <request> for <installation>`, `observed active version: <version or none>; staged version: <version or none>`, and `the next baley update can run`, then exits 0. A live claim refuses `update-check-busy` and exits 2. Other store errors use the shared CLI renderer and exit classes (`crates/baley/src/update/reconcile.rs:305-340`).

### baley doctor

- **Inputs:** `--host <name>`, default `claude-code`, the host whose wiring the host checks judge. Any other name is refused `unknown-host` with install's text and exit 2 before the ledger is opened or brought current (`crates/baley/src/ledger/args.rs:22-28`, `crates/baley/src/ledger/mod.rs:60-69`, `crates/baley/src/install/command.rs:45-54`). Beside it, the resolved home and config folders, the latest install record for the host, the placement map built from that record, and the placements derived from `HOME` and `CLAUDE_CONFIG_DIR`, the same derivation install and the guard use, which the hook and settings check reads to render install's entries. The executable is always the derived stable path, never the running binary. The install record tells installed from never installed: with no record every artifact is reported not installed, so a machine that has the binary and never ran install still reports each one so and raises nothing. With a record, a stub has its place when the record lists its identity, the registration, the hook and the settings when the record holds them, and the versions folder whenever a record exists. A `HOME` or `CLAUDE_CONFIG_DIR` that cannot place the artifacts, or a record that cannot be read, is reported and raises the exit status to 1, since an unreadable record is never taken for a machine where install never ran (`crates/baley/src/host_doctor/mod.rs:82-141, 304-336`, `crates/baley/src/ledger/commands.rs:122-198`, `crates/baley/src/host_doctor/report.rs:41-51`).
- **Outputs, built:** the ledger lines first, then a host section headed `Claude Code host checks` (`crates/baley/src/host_doctor/report.rs:38-206`), whose lines print in this order:
  - when the placements cannot be derived or the install record cannot be read, one line naming the cause and saying that no artifact can be checked. The lines that need the map (the install outcome, the artifacts, the stale stubs, the writable locations, the executable, the coverage and the guard hook) are then absent, and the rest print as below (`crates/baley/src/host_doctor/mod.rs:609-629`, `crates/baley/src/host_doctor/report.rs:41-51`);
  - whether the latest install finished, and whether it held the sandbox block back. Only a boolean `true` `complete` is a finished install, so a missing or mistyped field reads as partial. A held-back block is named with the reason and the settings file the record gives (`crates/baley/src/host_doctor/install_record.rs:30-41`, `crates/baley/src/host_doctor/report.rs:211-223`);
  - each artifact (the stubs, the registration, the hook and the settings) as not installed when the install record does not show it, as missing or unreadable when a place is given and the file is not usable, and otherwise as read. With a record, a hook the record does not hold is reported as not placed, since install places the hook only while something runnable is at the stable path (`crates/baley/src/host_doctor/mod.rs:340-443, 606-804`, `crates/baley/src/host_doctor/report.rs:55-130`);
  - each placed stub, the skill stubs and the thirty agent stubs alike, byte for byte against the manifest, which install, the guard and the doctor all read as the skill stubs followed by the agent stubs (`crates/baley/src/host_artifacts/stubs.rs:103-111`, `crates/baley/src/host_doctor/mod.rs:293-296`). A stub that differs is an older stub Baley placed when its SHA-256 is a hash the latest record holds for that identity, which install replaces, and any other differing stub is reported as differing, with both digests either way (`crates/baley/src/host_doctor/placed.rs:171-195`, `crates/baley/src/host_doctor/mod.rs:557-592`, `crates/baley/src/host_doctor/report.rs:82-97`);
  - the registration against the entry Baley renders for this binary, by the one rule install and composition use: the same `command` and `args`, `env` absent or empty, and `type` absent or `stdio`. An entry that sets `env` entries, or is of another transport, is reported as differing, with the entry found (`crates/baley/src/host_doctor/placed.rs:197-222`);
  - the placed hook and settings against what install writes. The hook holds the `PreToolUse` item install renders (the nine-tool matcher with a single command hook that runs the single-quoted stable path and `guard` within 10 seconds) and the item the record holds. The settings hold every `permissions.deny`, `sandbox.filesystem.denyRead` and `sandbox.filesystem.denyWrite` string install renders over the derived placements, which includes the versions folder's `Edit` rule and `denyWrite` entry and the stable path's, and every string the record lists. Entries are compared whole, so order, the owner's other entries and every other key never count. While the record says the sandbox block was held back, the rendered `denyRead` and `denyWrite` entries are not required, because install left them out on purpose, and the record's own entries still are. A file that lacks an entry is reported as differing from Baley's entries, naming each missing entry under its list. The settings file's SHA-256 is never compared with the `sandbox.sha256` the record holds (`crates/baley/src/host_doctor/drift.rs:21-99`, `crates/baley/src/host_doctor/report.rs:111-125`, `crates/baley/src/install/settings.rs:98-118`);
  - each stub the record lists that this binary no longer ships, by its recorded identity and path, reported as stale (`crates/baley/src/host_doctor/install_record.rs:44-67`, `crates/baley/src/host_doctor/report.rs:131-138`);
  - the stable path and the version its link points to, which new Claude Code sessions start, judged by `baley update`'s rule from the link alone with no program started. When the path holds something Baley does not manage, or cannot be examined, the line says why no staged version is known. It reports no running session's version (`crates/baley/src/host_doctor/mod.rs:531-545`, `crates/baley/src/host_doctor/report.rs:225-260`);
  - each folder install writes into, which exists only with a record: the stable path's folder, the versions folder, each placed stub's folder, the settings file's folder and the registration file's folder, each once. A location is writable when it is a folder this user may both write into and search, asked with `access`. One that exists and is not is a failed check naming the location and the cause. An absent one is reported and install creates it. One line says so when every location is writable (`crates/baley/src/host_doctor/writable.rs:32-62, 83-125`, `crates/baley/src/host_doctor/report.rs:262-290`);
  - the executable's kind: missing, a dangling link, not a regular file, or without an execute bit (`crates/baley/src/host_doctor/placed.rs:100-167`);
  - `bwrap` and `socat` on Linux, none on macOS and the sandbox unsupported on any other platform, looked up on the command's own `PATH` (`crates/baley/src/host_doctor/prerequisites.rs:75-194`, `crates/baley/src/host_doctor/report.rs:149`);
  - the coverage of Baley's folders per tool and per read or write, worded as configuration of the named documents and not as proof, with `Grep` and `Glob` best-effort ([0010](0010-guard.md) section 5), or one line saying why it was not judged (`crates/baley/src/host_doctor/report.rs:150-169`);
  - the nine-tool hook check, after the coverage lines: a `guard hook:` line saying a `PreToolUse` item runs the guard for all nine tools, or naming the tools it leaves out, and a line when `disableAllHooks` is true (`crates/baley/src/host_doctor/report.rs:170-193`);
  - the review providers whose API host the settings file's `sandbox.network.allowedDomains` allows, matched exactly against the catalog's API hosts and listed in catalog order. Any other host is the owner's and goes unnamed. A provider host is the owner's choice and never a gap (`crates/baley/src/host_doctor/provider_hosts.rs:29-44`, `crates/baley/src/host_doctor/report.rs:341-374`);
  - for each outside provider, whether a current acknowledgement covers it, by the interview's own rule: the stored warning version and the digest of the warning's text must both match this binary's. A provider acknowledged under another version or text is reported as not current, naming both versions and `baley config interview`, and one with no acknowledgement as none recorded. The read goes through `providers::record::read` and creates no `user` project on a fresh ledger (`crates/baley/src/host_doctor/acknowledgement.rs:32-60`, `crates/baley/src/host_doctor/report.rs:310-339`);
  - the effective global `updates.auto`, read and merged the way install reads it and not taken from the record's snapshot, with the file that sets it or the default, or unknown with the file to fix when the global settings cannot be read (`crates/baley/src/host_doctor/update_setting.rs:49-85`, `crates/baley/src/host_doctor/report.rs:292-308`);
  - the last recorded server call's `CLAUDE_PROJECT_DIR` and working directory on separate lines, read from the ledger and judged with the server's own rule (`crates/baley/src/host_doctor/server_context.rs:56-176`). An unusable variable is reported with `project-context-invalid`, the cause and what to set, and a missing one with `project-context-missing`. A working directory that differs from the project is valid and is not a finding. With no server call recorded, one line says so;
  - compatibility, where a ledger at a newer epoch is read-only for this binary, the write fence, where the server's startup `quick_check` is not observed from the command line and the `integrity_check` rows stand in for it, the home folder, and the config folder with a note when it is the home folder (`crates/baley/src/host_doctor/store_health.rs:49-63`, `crates/baley/src/host_doctor/report.rs:411-444`);
  - whether the guard's per-user records were behind this binary's when the doctor started, naming `baley rebuild user` (`crates/baley/src/host_doctor/guard_records.rs:38-78`).
- **Fixes:** every finding that raises the exit status names what to do. A refused placement or an unreadable record says to run `baley doctor` again once it is fixed. A missing placed file, a missing registration and an older stub say to run `baley install`, and a file that cannot be used or a stub that differs says to fix it or move it aside first. A differing registration gives install's own instruction, `claude mcp remove --scope user baley`, then `baley install`. A hook or settings file that differs, a partial install and a held-back sandbox block say to run `baley install` again. An unplaced hook, and an executable that cannot run, say to run `install.sh` or place the binary or a link to it at the stable path. A stale stub says to run `baley install`, which removes the stub's file when it still holds the recorded bytes and drops the record's entry. An unwritable location says to make it writable for the user and run `baley install` again. The guard check, `disableAllHooks` and the coverage gaps name the setting to change, and a missing sandbox program names the package to install (`crates/baley/src/host_doctor/report.rs:41-206, 549-628`).
- **Not read:** the doctor reads no key and tests no credential. It reports the version the stable path runs, which new sessions start, and reads no running session's version. The live qualification checks a session's version by asking it for `baley_version`.
- **Exit status:** placements or an install record that cannot be read, a gap in a given document, a placed file missing, unreadable or differing, a registration that differs, a placed hook or settings file that lacks an entry install renders or the record holds, an install that was partial, a sandbox block held back, a hook install withheld, a stub the record lists that this binary no longer ships, an older stub, an installed location that exists and is not writable, an executable that is missing, not a regular file or without an execute bit, a tool the hook leaves unguarded, `disableAllHooks` true in a hook or settings document, a missing sandbox program, an unsupported platform, a ledger at a newer epoch and guard records behind raise it to 1. An artifact that is not installed, the stable path's version, the provider hosts, the acknowledgements, the effective `updates.auto`, an installed location that is absent, the server's context and the folder lines do not. - **Limits:** only the documents given are judged. Other Claude Code settings files and `sandbox.enabledPlatforms` can change what applies. WSL1, containers that block bubblewrap, Ubuntu's AppArmor rule on user namespaces, ripgrep and the seccomp filter are not checked. A missing project variable is never seen from the ledger, because a server without it records nothing, so the doctor sees only a recorded project folder that is no longer a directory. The doctor reads a stub, like every placed file, through a symbolic link, while install refuses to write through one, so for a stub that is a link the line can name `baley install` as its fix though install will refuse it (`crates/baley/src/host_doctor/placed.rs:63-66`, `crates/baley/src/settings.rs:72-75`). There is no plugin, so there is no check of plugin defaults ([ADR 0038](../adr/0038-installer-and-opt-in-updates.md)).
- **Refusals:** `unknown-host`, as install refuses it, before the ledger is opened, with exit 2. A gap in a document names the setting to change, and a missing sandbox program names the package to install. An unwritable installed location is a failed check naming the location and its fix, with exit 1. The host checks read the ledger and the placed files, append nothing and write no file, and the acknowledgement read creates no `user` project. The store's own doctor runs before them and verifies each project's views, which first brings views behind this binary's current, so it can write the database. It appends no event.

## 6. Records

### install.recorded (event, per-user, `install` stream)

`baley install` records the ownership facts a run left, as the owner. The event goes on stream `install` in `user` at type version 1, with no upcasters, under command kind `install.record`, actor `owner`, policy version 0 and no caller. It is appended only when its payload differs from the latest record for the host, and a run that planned from an older record than the one now stored appends nothing (`crates/baley/src/install/event.rs:13-21, 111-140`, `crates/baley/src/install/record.rs:17, 47-118`).

| Field | Type | Meaning |
|---|---|---|
| `host` | `claude-code` | The host whose wiring was installed |
| `binary_version` | version | The version of the binary that ran install |
| `binary_path` | absolute path | The stable executable path |
| `complete` | bool | True only when every artifact is Baley's after the run, there is no gap, the catalog seed is recorded and no write or removal failed |
| `registered` | table | `registration`: the file's path and the whole `mcpServers.baley` entry that is Baley's after the run, or null. `hook`: the settings file's path and the whole `PreToolUse` item that is Baley's, or null |
| `stubs` | list | `identity`, `path` and `sha256` of every stub that is Baley's after the run, in manifest order: the skill stubs, then the thirty agent stubs. An entry names no kind: its path says where it was placed. A stub whose write failed keeps the previous record's entry. A stub this binary no longer ships that was not removed follows them with its previous entry |
| `sandbox` | table or null | `settings_path`, `sha256` of the settings file's bytes after the run, Baley's `home` and `config` folders, `write_only_files`, `write_only_folders`, and the entries Baley owns in `permissions_deny`, `deny_read` and `deny_write`. `held_back` says why the sandbox block was left out, or is null when it was written. Null when the settings file holds none of Baley's entries |
| `defaults` | table | Always empty: install applies no setting and records no provider acknowledgement |
| `updates` | table | `auto`, the effective `updates.auto` or null when the global settings could not be read, and `staged_version`, the version the stable path runs or null |

The whole entries are kept so a later run can recognise an older Baley entry and replace it. A matching name alone never does (section 5).

The interview's host step adds provider hosts to the same settings file after install has recorded it. It takes no install lock and records no `install.recorded`, so after it the `sha256` that `sandbox` holds is the digest of the file as install left it and predates the file. That is not drift: the doctor never compares the file's digest with `sandbox.sha256` and judges drift by Baley's own entries alone, so provider hosts the interview added never read as drift (`crates/baley/src/host_doctor/drift.rs:1-5, 48-99`), and the next `baley install` records the digest of the file as it finds it.

### work_order.issued and work_order.failed (events, the order's stream)

A work order is recorded as one `work_order.issued` on its subject's stream, `roadmap` for the start planner's order, and its failure as one `work_order.failed` on the same stream. Both are registered at version 1 with no upcasters. Neither payload holds a caller or a time: the envelope carries both, hashed with the event (`crates/baley-core/src/work_order/event.rs:14-48`).

| Event | Payload |
|---|---|
| `work_order.issued` | `id`, a lowercase UUID; `request`, the id of its chain's first order, its own id at attempt 1; `parent`, the failed order it retries, or null; `role`; `subject`; `attempt`; `route`, the route record ([0003](0003-configuration-and-routing.md) section 6); `agent`, the agent stub `bal-<role>-<rung>`; `instructions`, each `{identity, version, hash}`, in order; and `inputs`, each `{name, body}`, the body a reference to a `record` payload the event attaches |
| `work_order.failed` | `id`, the order, and `reason`, the session's plain words |

The `work_order` view holds one document per order, keyed by its id, with the issued payload's members and its `state`, `seq`, `recorded_at`, `failure`, `drafts` and `child` (section 5, `document`). An order is `pending` when issued, `failed` once `work_order.failed` names it, and `answered` once a `scope.submitted` whose caller carries its id names it, which also adds the draft's digest to its `drafts` once. A failed order stays failed when a later submission names it. A retry sets its parent's `child`. The view's `live` index runs over role, subject and state, newest first, so a transaction can declare that no pending start planner order exists (`crates/baley-core/src/work_order/view.rs:20-111`). The view raised the view set to 11.

### The caller on every recorded event

Every event a call records carries one `caller` in its envelope, hashed with the event. [Design 0001's Events table](0001-evidence-ledger.md#events) holds the exact keys, values and limits. The caller has two forms.

- The server form is what the server records for a request. It holds the project directory, the working directory, the host, the Baley session the server minted, and the call identity: the request's JSON-RPC id, with its source. It may also hold the client version, the host's own session id, a work order id and instruction evidence.
- The hook form is what the guard hook records for a tool call. It holds the host, the working directory and the call identity: Claude Code's tool-use id, with its source. It may also hold the project directory, the host's own session id, a work order id and instruction evidence. It has no Baley session, so a hook cannot claim one.

The guard hook fills the hook form on every record it makes in the per-user project `user` ([0010](0010-guard.md) section 6): Claude Code as the host, the hook's working directory and the call's `tool_use_id`, with `CLAUDE_PROJECT_DIR` as given and the host's session when the call has them. It sets no work order id or instruction evidence, and a call with no `tool_use_id`, or with a text the form refuses, is not recorded at all.

Instruction evidence is a list of entries, each an instruction's identity, version and hash. A session sends only an instruction's identity, as `instruction` on a `baley_apply` call. The server takes the version and hash from its compiled registry, and refuses an identity the registry does not serve. Reading an instruction records nothing. Every text is checked when the caller is built and again when it is read back, and each has a byte limit. A command-line command, the detached updater and a reconciliation have no caller: the envelope has no `caller` key, and a caller is never `null`. No caller enters a request digest or request key, so a replay records nothing and the original caller stays on the event the request first produced. The server's preparation fills the server form on checkout admission, the policy step and the prepared command ([section 8](#8-workflows)), and [section 11](#11-build-status) says which operations reach it.

### Update checks

Update checks are ordinary events in the per-user project `user`, with actor `owner` for a manual `baley update` and `baley` for a detached check, policy version 0 and no caller. The store records the attempt as `command.claimed` on `command/update.check`. Completion records one `update.checked` or `update.failed`, version 1, on `install` and closes the request with `command.completed` in the same transaction. Reconciliation also records the store's `command.reconciled`. There is no separate update-check table, and update events have no projector. The `install` view above holds install records only; update events are read from their stream (`crates/baley/src/update/events.rs:17-30`, `crates/baley/src/update/record.rs:32-82`).

| Event | Inline facts |
|---|---|
| `update.checked` | `installation` (absolute stable path text, never the link target), `day` (UTC `YYYY-MM-DD`), `claim: {request_id, seq}`, `checked_at`, `outcome` (`current` or `staged`), `active_version`, `staged_version` |
| `update.failed` | `installation`, `day`, `claim: {request_id, seq}`, `observed_at`, `code` (one of section 5's eight delivery failure codes), `active_version`, `staged_version`. An interrupted attempt records `code: "update-interrupted"` and never counts as a successful check |

Version fields are strings when known and `null` otherwise. `claim.seq` is the sequence of the original `command.claimed` event. The completion keeps the claim's day even if it finishes after midnight. The `staged` outcome means the version was both staged and activated, so both version fields name it. An offered version appears in the current receipt, not in the event payload (`crates/baley/src/update/events.rs:127-180`, `crates/baley/src/update/receipt.rs:51-74`).

**Daily claim.** The updater uses the existing [0001 command claim and scope protocol](0001-evidence-ledger.md#commands), without a new port operation. Both manual and detached checks submit `update.check` with a fresh request UUID and exact scope token `update/<installation>`. The intent is exactly `{installation, day}`. `installation` is the absolute stable path as installed (`~/.local/bin/baley` with the home expanded), never its link target, so activation does not change the identity. `day` is the UTC calendar date from the supplied time. The command digest binds the command kind, project, intent, actor, policy version and scope. The claim owner carries the process id as decimal text, `host_session: "cli"` and the supplied start time. Only the detached check's decision calls `Transaction::event_exists` inside the claim transaction, matching `command.claimed` on `command/update.check`, with top-level fields `kind: "update.check"` and `intent` equal to that object. An existing claim, manual or detached, refuses that detached check with `update-check-not-due`. The manual decision never refuses for that reason. For an allowed decision the existing `claim` appends the claim and takes its lease in that writer turn, before any network work. The shared scope blocks overlapping checks, including across midnight. After completion releases the scope, another manual check may claim it under a fresh request that day. A failed or interrupted attempt also covers that day's automatic check; it does not prevent a fresh manual attempt after the scope is released (`crates/baley/src/update/claim.rs:62-169`).

Only `Claimed::New` permits fetching. `InProgress`, `Replayed`, a blocked scope or a refused decision never fetches. The anchor ticker renews the lease while the check runs, and renewal stops before `complete`. The updater also confirms the lease and its ownership immediately before staging and activation. A lost claim or failed confirmation stops the next effect with `update-interrupted` (`crates/baley/src/update/claim.rs:171-245`, `crates/baley/src/update/command.rs:186-239, 334-392`).

When a check finds an interrupted installation scope, it reconciles from the stable link and local version folders without re-executing the interrupted network check. A managed active link is enough to close the interrupted claim with `update.failed` and `update-interrupted`. A stable path Baley does not manage is ambiguous: missing, not a link, a link with a target outside the exact managed form, dangling or not pointing to a regular file. Automatic reconciliation then records a finding and leaves the claim held for the owner without an update result event. It does not infer a successful check from an observed activation. The highest local version above the active version is recorded as staged, or the highest local version when no active version is known (`crates/baley/src/update/reconcile.rs:45-169`).

Both forms of reconciliation use command kind `update.reconcile`, policy version 0 and no caller. The actor distinguishes them: `baley` with `ReconcileAuthority::Automatic`, `owner` with `ReconcileAuthority::Owner` through `baley update resolve`. Owner resolution can close an ambiguous claim and release its installation scope. After automatic resolution, the check tries a fresh claim once; that new claim still obeys the detached daily rule. Store fencing or unavailable state prevents a new check, and a completion failure after activation reports the new active version and the incomplete record (`crates/baley/src/update/reconcile.rs:171-303`, `crates/baley/src/update/command.rs:140-161`).

Provider risk acknowledgements are the per-user records in [0003 section 6](0003-configuration-and-routing.md#6-records), not inferred from an install receipt.

The text of every instruction is owned by the area it serves; this area serves it.

Each instruction is compiled into the binary with an identity, a version and a hash.
